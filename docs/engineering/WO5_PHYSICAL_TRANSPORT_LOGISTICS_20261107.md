# WO5 — Physical transport, logistics, and resource-demand integration
**Opened 2026-11-07**, owner-directed Stage 5. Branch `industry/wo5-physical-logistics-20261107` stacks on WO4 draft PR #91; WO4 stacks on WO3 #89.

## Binding architecture and scope
- The game begins with finite physically constructed ships, planetary shuttles, storage, fuel and original NPC pilots. No free carrier, automatically completed shipment, arbitrary planetary goods, transport speed, trade credit, wage or material creation.
- `Simulation` and `PersistentWorld` remain the only stock, NPC and ship authority. Original `UniversalTransport`, `IntercolonyFreightLeg`, `LocalDeliveryOrder`, `ThirdPartyRegistry` and `RegionalHostCommands` already exist; WO5 must extend/compose rather than replace them.
- WO4 `CarrierRequest` and `ProposedMaterialFreight` are **read-only unbooked suggestions**, never arrival receipts or owner approvals. Every operation must be owner-authenticated by the trusted host and recheck the current original world, not a copied demand snapshot.
- The actual original local pickup supports **Water, Food, Nutrients**. The original two-leg sealed intercolony freight supports these same three, NOT oxygen or arbitrary manufactured objects. The separate original planetary shuttle supports Water, Food, Nutrients, Oxygen for one local trip. Finished panel/frame cargo has its own original `ThirdPartyRegistry` path and requires real constructed workshops, distinct owner approvals and warehouse custody.
- WO3-F remains open due pre-runner CI infrastructure; WO4-F remains open until genuine native test logs. Neither blocks Stage 5 development. Native Windows 3D installed-game acceptance stays deferred until genuine 3D assets.

### Real original-world interfaces
- New `include/galaxy/WO5ManufacturedFreight.hpp` converts a **recipient-declared `economy04::MaterialNeed`** (real physically constructed receiving warehouse, priority and required quantity) into an ephemeral offer for a **specific original factory-returned physical lot** in an existing source warehouse.

The existing `ProductionShippingHost::book_factory_goods` checks the **original v53 `sg_v53_world_return` SQLite factory proof** for the exact `plates`/`frames` item, source site, source ship and amount, then the existing `ThirdPartyRegistry` commits the unique v56/v57 booking and prevents colliding cargo reservations. - Original separate immutable source-owner (role 1), carrier-owner (role 2) and receiving-owner (role 3) approvals are **not** auto-created by WO5-C. - `include/galaxy/WO5ManufacturedEvidence.hpp` is a read-only reconciliation of `ShipmentStatusView` (SQLite original custody receipts) against actual original physical warehouse and carrier stock. It distinguishes unsigned booking, dispatched but unloaded, physically loaded/in transit, genuinely received, and two-owner settled; returned or redirected consignments are **not** misreported as direct fulfillment, and an unrelated caller receives no shipment record. ## WO5-E — Regional ownership and physical-custody recovery (2026-11-07)

**Status: SOURCE IMPLEMENTED, exact-head Linux/Windows native execution and repair remain OPEN.** See [WO5 draft PR #92](https://github.com/vjmichael/Single-galaxy/pull/92). This work deliberately preserves the game's *single original physical world and original regional checkpoint*, rather than introducing a second live freight or goods ledger.

### Proven existing authority and actual new enforcement

- Existing `RegionalModeAuthority::{prepare,commit,abort}` owns SQLite-enrolled `Cold` / `Detailed` exclusivity, pending freeze, generation rotation and optimistic checkpoint revision. Existing `shipping::seal_regional_shipment_boundary` commits a **v59 immutable manufactured-goods receipt-prefix witness in the same SQLite owner-transfer transaction**; `verify_regional_shipment_boundaries` detects historical manufactured shipment replays/forged or deleted receipts on reload.
- **Gap closed:** v59 covers factory-returned panel/frame goods, *not* the original native `LocalDeliveryOrder` → `IntercolonyFreightLeg` pathway (water, food, nutrients), whose live physical source/pilot/cargo/final arrival state is in the canonical `Simulation`. Previously the regional owner could promote or demote without checking a pending or loaded native vital-freight leg.
- New `include/galaxy/WO5RegionalFreightFence.hpp` reads **the latest original SQLite world snapshot inside the same `RegionalModeAuthority` `BEGIN IMMEDIATE` transaction**, reconstructs the original `Simulation`, validates its stored native world checksum, and **refuses an owner handoff while any native intercolony freight is `AwaitingPickup` or `Loaded`**. For already `Delivered` native shipments, it requires original final cargo removal and actual celestial-arrival receipts via `WO5FreightEvidence`. Both `prepare` and `commit` enforce the fence, so work cannot slip through a prepared transition. Denial rolls back the owner state; no pending or loaded cargo is reassigned to Cold or manufactured into a macro double-delivery.
- **Conservative global fence, explicitly intentional:** Original native intercolony freight does **not yet have an authenticated ship→region-scope mapping** in the original world. Therefore **any** unresolved native freight blocks **all** owner cutovers in that one physical SQLite world, even for an otherwise unrelated region. This is a real scalability tradeoff, not a claim to region-local precision. Do not weaken the fence until a durable, verified native region-binding exists. The existing scope-specific v59 manufactured shipment history remains separately validated and does not incur this broad vital-freight freeze.
- **Reused real carrier repair:** `WO5FreightEvidence.hpp` no longer treats every later kilogram of the same resource on a reused carrier as part of an older delivered shipment. A delivered lot is verified from its own *completed arrival receipt*, while any remaining live carrier kg must be fully accounted for by **separately identified currently-Loaded native freight legs**. Old delivered evidence remains valid; a new 100 kg shipment does not resurrect or double-deliver an earlier 200 kg job.

### Read-only same-database reconciliation (no silent authorization)

- New `include/galaxy/WO5RegionalRecovery.hpp` exposes `observe_native_regional_recovery`. It binds a trusted, scoped `RegionalModeAuthority` and `CheckpointStore` to the **same actual SQLite filename** as the original `PersistentWorld`; compares the original latest durable snapshot generation and hash against the live physical runtime; checks exact current `generation`, `checkpoint_revision`, `boundary_tick`, Cold/Detailed owner and pending phase, and independently re-verifies immutable v59 manufactured-cutover receipt prefixes.
- The audit attributes original owner-scoped vital shipments to **AwaitingPickup, Loaded or original-receipt-proved Delivered**, rejects missing physical cargo/original receipts, exposes `has_unresolved_original_freight`, and never creates a claim to regional stock. Cold, pending or stale-owner generations report **no Detailed-only execution eligibility**; stable Detailed may only be *considered* for further host checking. This observation **never** acts as transport authorization. Original host effect writers must independently perform their own atomic owner-epoch/physical-source checks at commit, not rely on this earlier read-only report.
- Minimal read-only identity interfaces `CheckpointStore::database_path()` and `RegionalModeAuthority::{database_path,scope}()` prevent accidentally pairing independent SQLite stores with matching but unrelated counters. The original `sqlite3*` write connection remains private. A separate SQLite file with the same scope, revision, boundary and generation cannot borrow the physical world.
- **Unsupported:** native vital-freight loads are **not** automatically migrated between Detailed and Cold. Until a correct region-scoped physical custody transfer and matching regional consumption/transport semantics exist, the handoff is safely refused. The source is conservative, does not simulate or guarantee cross-region auto-routing, and is not a second independent shipment engine.
