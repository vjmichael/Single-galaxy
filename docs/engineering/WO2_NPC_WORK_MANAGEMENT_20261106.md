# WO2 — NPC work and management (owner-directed second work order)
**Started 2026-11-06.** Stacked on [WO1 industry catalog draft PR #87](https://github.com/vjmichael/Single-galaxy/pull/87). No new player gameplay, economy currencies, planetary settlement rules, 3D assets or multiplayer.

## Engineering scope
1. Map **every WO1 production capability** (including loss-bearing recovery) and **every WO1 service role** onto explicit NPC trades/professions, required station/facility, power, staffing, skill families, experience/training path and supervising job where appropriate. This is a dictionary of *potential work*; item prototypes must not be interpreted as already operational factories.
2. Preserve original NPC identity, actual location, home-colony authority, illness/medical duty, transit/flight occupation, existing shipyard assignments, existing workshop staff, and real utility/power/material capacity. **Never spawn a worker or issue an independent parallel work receipt.**
3. Introduce an **auditable, deterministic read-only industrial workforce planner** for the two real original workshop operations: panel forming and frame finishing. It may recommend an existing available named NPC, or explain why the site is blocked; never imply a staffing order was executed.
4. Produce an **explicit owner-approved original `Command` admission envelope**, using `AssignWorkshopOperator` or `AssignWorkshopFinisher` through the original `PersistentWorld::submit` and commit tick. Host authenticates owner; a viewer request or absence of consent cannot become an approved order.
5. Protect exclusive named worker slots against conflicts with already occupied workshop stations, native shipyard build crews, active medical shifts, travel and other native duty, without breaking old-save semantics. No blanket claims of actual qualifications for professions whose educational infrastructure is not yet built.
6. Reuse original workshop power, feed, finisher installation, backpressure, work-in-progress and SQLite journal for actual production/restart evidence. New skill/management data is **capability configuration**, not independently mutable NPC biographies.
7. Define scalable staff/shift, mentorship and manager capacity **contracts** for later work, but do not fake per-person XP or work histories from generic factory batch totals.

## Exit gates
- Every WO1 site capability / production recipe / loss-bearing recovery and every service staff role has exactly one mapped profession profile; schema tests reject gaps and invalid privileged/native bindings.
- Deterministic two-slot original-workshop staffing recommendations, graceful no-staff, no-power, no-input, unbuilt-finisher and worker-taken cases; no cross-owner or offline/oracle assignment.
- Explicit owner-authenticated command into original world with durable SQLite admission/effect and recover-copy; repeat/replay cannot duplicate a worker or create production.
- Native C++ Windows/Linux compile and original worker/industry/SQLite CTest; source-generated schema parity; no security/legacy regressions.
- If source code is complete but CI is still queued, label source complete and native acceptance **pending**, never claim tests passed.

**Scope boundaries:** WO3 will decide which planet facilities can be constructed and kept supplied; WO4/5 will distribute and physically deliver their goods; WO7 society will interpret NPC preferences/household outcomes. Work definitions make no automatic colony-owner decisions.

### WO2-I — Owner-approved durable workshop shifts (source implementation, native acceptance OPEN)

**Scope implemented on the original game world:**

- Original `Action::StartWorkshopShift` and `Action::CancelWorkshopShift` route through the existing authenticated owner ship, installed outpost workshop, original `Command`, `PersistentWorld::submit`, committed simulation tick, and SQLite receipts. These do not spawn workers, mint work XP, change materials or create a second workforce scheduler.
- Shift admission carries the **original due tick as its start**, `thrust_x` as installed workshop slot (1=cut, 2=shape), `amount` as the existing named worker, and `thrust_y` as the bounded duration. Start and duration are **1–10,000 original ticks into the future / long**. Future commands are durable but **not guaranteed** to execute until their exact original-world tick rechecks ownership, physical co-location, health, duty, real installed station, no already-installed worker, shipyard work, and medical interval conflicts.
- The successful start stores one `WorkshopShift` **inside `OutpostWorkshop::shifts`**, and assigns the original machine's named operator/finisher slot. No employee copies or separate payroll exist. The installed production kernel remains the only manufacturer; it conserves its original 20 kg WIP, input, output, scrap, and utility constraints. A long shift cannot itself mint production.
- The simulation releases the named machine assignment automatically at its end-exclusive tick. Losing actual NPC identity/location/health/duty also stops the shift rather than allowing an orphan operator to continue production. Original WIP pauses and can resume only when an actual available worker is approved again.
- An owner may cancel an active shift using its original start-command ID, or **cancel a still-pending future start with enough lead time** to commit the cancellation first. The future original command remains journaled and later emits a rejected event; it is not erased from accepted history. Cancellation tombstones live in the same original workshop snapshot, are bounded to 256 per site, and are pruned when that original start reaches its due tick. Repeated, stale, foreign or unauthorized cancellation fails. Owner-directed **immediate atomic relief** now uses one owner-approved `RelieveWorkshopShift` command to switch the physically present worker while retaining the same original start-command ID, end-exclusive tick, machine WIP and material ledger. Separately, multiple advance-approved nonoverlapping future shifts can start at the exact end-exclusive tick of the preceding shift without a gap, provided the original execution gates still pass.
- v106 canonical world snapshots add only original site-owned `workshopshift` and `workshopshiftcancel` records. Restore refuses duplicates, invalid windows, nonexistent sites or workers, mismatched installed slot/worker, missing original applied shift evidence, or cancellations with no pending matching original order. SQLite recovery independently checks original command/owner/site/worker/slot/time envelopes and applied shift/cancel receipts. v1–v105 snapshots remain on their existing versioned paths.
- Existing `WO2IndustryWorkforceTests.cpp` now covers owner proposal refusal; future pending command SQLite copy; actual activation; snapshot forgery rejection; approved active cancellation; original shift expiry; release and reassignment; same-tick end-exclusive handoff between independently approved consecutive shifts; overlapping future slot/worker refusal; future cancellation persisted as a tombstone and subsequently rejected original due command; retained mass on all paths.
