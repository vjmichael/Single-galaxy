# SHIP-STATUS-07D — Authenticated Hail & Colony Security Case Desk

Status: **implementation committed in stacked draft PR; independent Windows/Linux native and graphical acceptance not yet demonstrated.** This work extends SHIP-STATUS-07 PR #84 without changing lethal ship combat scope.

## Product semantics

A sensor sighting is a vessel description, not a player identity. Players and NPCs may choose to remain silent. A voluntary hail discloses the currently authenticated controller of the *actual* physical hull; it never retrospectively proves who flew that hull when an earlier alleged offense occurred. A refused or acknowledged existing warning is a different state from voluntary hailing. No warning, trespass, sentence, confiscation, armed intercept, or criminal conviction is automatically generated by volunteering to hail.

A previously witnessed, genuinely applied or resisted cyberattack is recorded with a named current NPC witness, original attack command receipt, physical ship silhouette and actual territorial jurisdiction. The casebook stores sealed original hull provenance for later evidence reconciliation while the owner-facing public read model preserves anonymity until a verified later hail. Similar-looking ships only generate *investigative leads*, not unique identity or actionable proof of guilt.

## Native host integration (one original game writer)

- `TerritoryJournal::voluntary_hail` appends a new `TerritoryEventKind::VoluntaryHail` (kind 9) into the **existing immutable SQLite territorial journal**, requiring the session-authenticated visiting owner, original physically owned visiting ship, existing foreign territorial claim, current named on-duty colony observer and real sensor detection. This preserves the earlier warning and trespass semantics unchanged; no automatic receipt is invented.
- `CyberIncidentJournal::link_authenticated_hail` accepts either an original verified warning response or same-tick original verified voluntary hail. It appends separate immutable original-hull/controller identity evidence; the earlier cyber incident remains untouched. A voluntary hail without an existing cyber incident is still a valid territorial identity receipt; there is simply no older case to link.
- `SecurityDeskHost.hpp` binds the trusted session owner, existing colony ship, current selected physical pilot hull, original `TerritoryJournal` and `CyberIncidentJournal` with the original NPC watch and original nonviolent patrol dispatcher.
- On original-world startup and after each committed simulation tick, `capture_current_tick` checks only **actual same-tick native HackConfuse Applied/AttackResisted receipts** and case intake of already claimed real territory with real on-duty NPC witnesses. It deduplicates command/jurisdiction receipts on restart. A failed separate journal write leaves original combat untouched; the host reports an unavailable index, not a fake successful case.
- `src/colony_live_host.cpp` instantiates both append-only journals on the exact original SQLite world path while the existing host writer lease remains authoritative. The isolated security service does **not** launch a second simulation or host.
- Native commands after authenticated `AUTH|7|...` (the current desktop host owns local player 7) include `SECURITY_REFRESH`, `SECURITY_CLAIM|radius`, `SECURITY_WARN|foreignTrack`, `SECURITY_HAIL|foreignColony`, `SECURITY_REPLY|foreignColony|actualNoticeId|ACK/REFUSE`, `SECURITY_PATROL|nativeCaseId|observedTrack`. All case/hail/observer/reply identities are independently rechecked by the original journals. An unprefixed security command and a foreign principal fail closed.
- `SECURITY_PATROL` is explicitly **nonviolent** and requires original strong sensor hardware, a current physical description match, and original NPC flight capacity. Neither a matching silhouette nor an authenticated hail becomes a warrant.

## Transport and presentation

- `live/interactive_relay.py` adds exact-shape authenticated POST `colonySecurityRefresh`, `colonySecurityClaim`, `colonySecurityWarn`, `colonySecurityHail`, `colonySecurityReply`, and `colonySecurityPatrol`. The existing local account cookie, trusted mapped player ID, CSRF token and same-origin JSON validation remain enforced. No request can supply a different owner, crime verdict, NPC witness, damage or seizure authority.
- A case ID may require 62 bits, so a client sends its **canonical decimal string**, never a JavaScript Number that would silently round. The same rule now applies to original signed-63-bit territorial warning IDs, hail identity receipts and security result receipts; the relay validates canonical digits and upper bounds before conversion back to native integer authority.
- Native `COLONY|1|tick|SECURITY_*` telemetry includes home-jurisdiction status, bounded owner-scoped case rows, anonymous acquired foreign tracks, pending notices for the authenticated visiting owner's ships, physically witnessed foreign claimed jurisdictions and verified result receipts. Sensor descriptions are ASCII-hex encoded across the delimiter-based event protocol, then escaped using browser `textContent`.
- `viewer/security-desk.js` parses strict native frames, uses selected *actual* piloted ship, enforces disabled controls, renders case details with a difference between *culprit unidentified* and *later authenticated controller*, and updates on native receipts only. It never shows a client-generated conviction.
- `viewer/interactive.js` now routes those native frames, refreshes after authenticated reconnect, and destroys private case state on logout. `viewer/interactive.html` adds owner-facing claims, contacts, cases, voluntary hail, incoming warnings and investigative patrol controls.
- Current genesis deliberately has one player colony ship, finite crew, no pre-generated other colonies, criminals or NPC cyber cases. Consequently real fresh-game security and voluntary-hail targets remain empty until physical worlds/claims/encounters exist; the UI must not invent opponents to demonstrate the system.
- **Scope boundary:** present local relay/session is still single-home-owner desktop (`playerId=7`). The native core supports an actual foreign visiting owner, including NPC owners in its existing world, and verifies the original hull; broader multi-user account login and server-side NPC response automation are not added here. The local security desk is owner-scoped; publishing reports to a shared multiplayer service and a judicial system remain later work.
