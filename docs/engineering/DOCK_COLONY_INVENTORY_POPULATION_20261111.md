# Dock District, Colony Inventory, Population LOD and On-Foot Movement

Engineering design and implementation register — 2026-11-11. **Development branch, not a verified release**. No routine CI, draft PR, native acceptance or packaging submissions are authorized during this building phase.

## Player-approved governing design

The dock is the interface between a physically situated colony and space. It is a **separate transport/logistics district** with a protected public boarding path, freight staging, and a named-worker dispatch area. The colony can have a population in the millions, but rendering and pathfinding every resident is forbidden. Its original simulation may aggregate people; only a bounded small fraction appears in Godot, and that display must never invent inventory, job outcomes or actual NPC identity.

Inventory has **EVE-like location custody**: one logical, private inventory for each owner at each colony/station (the native `(station EntityId, PlayerId)` hangar plus native owned station facilities). An item left at Colony A cannot be accessed at Colony B; it must be loaded into a physical ship and transported. Do not create an account-global stash or copy inventory into UI memory as a second authority.

The player's docked-ship ore is transferred by native `UnloadOre` to the exact owner's **colony station hangar**, not the avatar's pocket. Refining at Colony A works from the same colony interface and requires an actual original-world constructed, crewed, powered facility, with source lot, finite inputs and original SQLite commit receipt. The interface is permitted anywhere **inside that original colony**, so players do not have to walk to the actual refinery or factory for control. Physical construction, material transfer, equipment, NPC assignments and logistics remain real; only the operator's local console access is virtual.

Manufacturing/ship-module design is **deferred**; no artificial recipe or module provisioning may be used to fill the gap. The eventual manufacturing panel must issue original approved industry/workshop commands and deposit legitimate output at the **same colony**, not at a remote station or on the person.

On foot, pressing **Shift** toggles running ON/OFF; holding Shift is not required. Flight remains the original supervised third-person cockpit with separate inputs.

## DOCK-02 implementation — added in this task group (source only)

- `include/galaxy/DockLogistics.hpp` persists authorized dock-shift appointments and bounded service jobs in `dock_staff_v1` and `dock_jobs_v1` **inside the original saved-world SQLite file**. These tables reference existing named `NpcRecord` identities and original ship IDs; they contain **no ore, people, manufactured stock or second hangar**. One worker can hold at most one dock shift at a time in this table; shifts expire after 256 original-world ticks, and only a physically present same-owner named ship-role NPC free of known native workshop/medical/yard work may be assigned. Existing external workforce schedulers do not yet honor the dock reservation; this remains a cross-system integration gap.
- One station/owner can have up to **16 valid on-shift dock workers**, **128 outstanding jobs total** (including held jobs), and up to **64 tonnes in one finite, ship-backed freight booking**. Both booking and execution revalidate native original-world custody; a queue request does not claim that inventory moved. Passenger bookings require a real, physically present, same-owner named NPC and are **check-in only**, with no fictitious voyage or transport ID.
- `src/desktop_station_host.cpp` implements `DOCKVIEW`, `DOCKASSIGN`, `DOCKRELEASE`, `DOCKPASS`, `DOCKFREIGHT` and `DOCKWORK`, with original PERSON/session/generation/replay/45ms/colony locality checks. Worker auto-selection examines **at most 4096** original named NPCs (a truncated search may refuse without inventing staff). No extra writer process or account-wide supply is created.
- Work dispatch is bounded by the number of real available assigned workers: at most **min(active dock staff, 4)** original appointments per explicit dispatch. Cargo service uses the existing authoritative `Action::UnloadOre`, one real tonne per original `PersistentWorld::step()`. Stable command IDs are reserved *before* dispatch, so an interrupted post-commit acknowledgement can reconcile an original `Event`; missing/ambiguous evidence marks a job **held**, never automatically repeats ore transfer. A passenger check-in simply commits its appointment in SQLite; it does not alter physical passenger custody.
- `desktop_godot/world/native_station_session.gd`, `refinery_terminal_ui.gd` and `main.gd` expose worker assignment/release, status refresh, bounded passenger check-in, one-tonne physical freight booking and explicitly requested worker dispatch in the ordinary **I** colony panel. No raw IDs are required. Native `DOCK` receipts bind identity, station, queue bounds, generation and the outstanding request. `POPVIEW` now reports **valid assigned dock shifts** instead of mistaking a generic ship-role NPC for an employed dock worker.
- `tests/DockLogisticsTests.cpp` and CMake registration stage the first conservative false-worker/false-passenger/undocked-freight/restart checks. **They have not been executed. No native build, installed gameplay matrix, CI submission, PR verification or release acceptance is claimed.**

## DOCK-02 limits that still need implementation

1. **Original-world station staffing availability:** fresh-world starter ship crew generally remain aboard their own real ship. A genuine named-NPC disembark, local recruitment, shift-training and station custody path is still required for the first usable station shift. Never count crew merely because a ship is docked.
2. **Global workforce reservation:** existing workshop/yard/medical schedulers must reject a worker already appointed to a dock shift; the dock currently checks their duties on both assignment and actual execution but cannot prevent them being assigned a different job later.
3. **Continuous service:** the current native host advances queues only on an explicit creator dispatch; independent scheduled background work, shift handoffs, priority/fairness, passenger manifests and physical boarding/voyage admission are separate implementation work. A passenger check-in is **not** a completed travel.
4. **Recovery and lifecycle:** held jobs conservatively block reuse, but an owner-reviewed cancellation/reconciliation interface and a bounded archival/aggregate counter for lifetime queue history are not built yet. Existing direct manual one-tonne `COLUNLOAD` remains available outside this staff-scaled service queue.
5. **Scale:** the LOD caps are constant (24 civilian + 8 staff graphics), but colony-wide millions-scale cohort population statistics, aggregate traffic demand generation and owner-approved transport admission are not yet connected to the visible native named-NPC sample.
