## GK-L — owned delegated Linux cgroup v2 (not process-group substitution)

Native `galaxy_server_dx_supervisor` has an explicit opt-in `--delegated-cgroup-root <owned-unit-root> --worker-uid <nonzero> --worker-gid <nonzero>` admission. It requires the selected systemd service's own non-root cgroup path (not `/sys/fs/cgroup`, a sibling, or an ancestor); verifies cgroup-v2 and `cgroup.kill`; creates a unique empty child leaf; forks but **does not execute the worker until the parent has written its original PID to `cgroup.procs` and verified `/proc/PID/cgroup` and populated `cgroup.events`**. After the gate is released, the worker drops *all supplementary groups*, assumes a distinct UID/GID and sets `no_new_privs`. Thus it does not inherit the supervisor-owned ancestor cgroup-procs write privilege. Timeout/cancellation/worker exit use the kernel `cgroup.kill` followed by an empty-leaf verification and removal. A reported success cannot hide an active descendant in the leaf. Existing normal users and hosted native CTests continue using their unchanged process-group/PDEATHSIG supervisor, **not** a claimed delegated cgroup.

`tests/Stage06GDelegatedCgroupAcceptance.py` always checks negative / missing / wrong-role admission on native Linux (and OS-option rejection on Windows). Its **positive** mode requires a *pre-existing*, separately delegated systemd-owned cgroup service and a distinct finite worker UID/GID; it runs an actual hostile **ancestor `cgroup.procs` migration attempt** and a **setsid-detached descendant** that must be killed by `cgroup.kill`, then checks leaf cleanup and records original binary hashes. Failing these checks is a BLOCK, not a fallback to `killpg`. The optional `tools/stage06g/Stage06G-Linux-Delegated-Cgroup.service.example` is an uninstalled operator template; it never delegates privileges or enables a service. The physical operator must also independently kill the actual service MainPID and inspect the OS journal/unit cgroup for all descendant deaths; passing the positive fixture alone **does not close systemd guardian-death custody**.

**Current local environment:** `/sys/fs/cgroup` is mounted read-only, `/proc/self/cgroup` is `0::/`, and there is no delegated systemd outer unit. Positive GK-L is **BLOCKED here**; only fail-closed admission and original process-tree tests can run. Do not claim a rootful Docker container or `kill(-pid)` as delegated acceptance.

## GK-W — Windows SCM / Job Object physical evidence

New Windows-only source target `galaxy_stage6g_windows_scm_gate` has a real SCM `ServiceMain` and stop handler. It is a **finite diagnostic fixture**, not a generic command service and not a Windows game installer. It launches only the real `galaxy_server_dx_fault_child descendant` executable, suspended; assigns it to a `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` Job before resuming; requires a native kernel `JobObjectBasicProcessIdList` with the child **and its real grandchild**; then waits for SCM STOP, closes the Job and independently waits on both original Windows process handles. It writes original `job-start.json` and `job-stop.json` receipts with the source SHA, service PID, worker PID and Job membership.

The default `tools/stage06g/Stage06G-Windows-SCMJob-Acceptance.ps1` action is **preflight only**. Physical execution requires an explicit `-ExecuteOneUse` on a *clean checkout at the exact SHA*, native MSVC x64 executables and an elevated Windows console. It refuses an existing service or prior evidence directory; creates only the fixed disposable `SingleGalaxyS6GKernelGate` service, runs under `LocalService`, applies a private ACL, and verifies two genuine STOP/START lifetimes, kernel Job descendant deaths and a different service PID on restart. The script deletes its test service in `finally`, retaining private receipts. No NSIS, game installation, GPU or external network step is involved.

**Current gate:** code exists for native Windows compilation and physical acceptance, but **physical Windows SCM execution and its kernel receipts have NOT been obtained**. Hosted `windows-2022` Job tests are useful regression evidence, not a substitute for the owner's actual Windows machine or installed game.

## GR — production-scale **native multi-world** crash/recovery workload

`Stage06GMultiWorldRecovery.py` simultaneously starts four *independent* real `galaxy_desktop_player_host --planet` worlds, each owning a different SQLite game file, supervises **at least 256 committed authoritative ticks per original world (1,024 aggregate)**, injects guardian death, rejects overlapping writers, verifies no offline ticks, restarts each from durable SQLite and denies stale session actions. Each records a nine-tile original source terrain packet, with SHA-256 and a distinct session. It emits an exact-head machine-readable summary when the native test runner passes `--output`.

This is concurrent original-world production **load/recovery engineering**, NOT proof of networking, live multi-cell cross-region consistency, indefinite-scale throughput, physical Windows service lifecycle, delegated Linux kernel containment, or installed Radeon playability. Existing four-cell 1,024-tick within-world and 4,000 native worker-launch tests remain mandatory in addition to this new workload.
